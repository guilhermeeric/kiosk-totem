# Coupon Codes Implementation Plan

> **For Hermes:** Use test-driven-development skill. Implement task-by-task, one conventional commit per green gate (repo AGENTS.md rule). Vertical slices, RED-GREEN-REFACTOR each task.

**Goal:** Customers can apply a coupon code to their cart; a successful apply snapshots the coupon's discount **percent** onto the cart, the granted discount is the percent of the current subtotal (rounded half-up to cents), and the order records the coupon code + granted money discount at checkout. Coupon usage is limited: each coupon carries a quantity of remaining paid redemptions, consumed once per paid order (row-locked, inside the checkout transaction).

**Architecture:** Coupon is a new domain entity (own table, repository ABC, no admin CRUD — rows arrive via seed/migration only). Application rules are **deep**: `Coupon.add(cart, now)` owns the applicability gates (not expired, uses left, percent in (0, 100]) and the snapshot attach in one call — the usecase never checks validity itself, it only resolves existence (404, the repo's seam) and persists. Usage is limited like items stock: `coupons.quantity` counts remaining paid redemptions and is decremented once per paid order, in the checkout transaction, **after** the payment attempt succeeds — redemption is a paid-event side effect, never a pre-payment reservation. The discount lives at the cart/order aggregate level, never on item lines: lines keep their list-price snapshot (the documented "full price story"), and the coupon rides as `coupon_code` + `coupon_percent` on `carts` (percent snapshotted at apply) and `coupon_code` + `coupon_discount` (granted money) on `orders`. The snapshot is honored at checkout — no re-read of the coupon row, no revalidation (user decision: honor once successfully applied). The percent bound (0, 100] is what keeps the discount proportional — it can never exceed the subtotal, so the total never goes below zero.

**Tech Stack:** FastAPI + asyncpg + Postgres (liquibase migrations), Vue 3 + Vite + vitest + TanStack Query.

## Locked decisions (user-approved)

1. **Cart-level discount (Option B).** Lines keep list-price snapshot; `carts` gains `coupon_code` + `coupon_percent`; `orders` gains `coupon_code` + `coupon_discount` (granted money). No per-line price mutation.
2. **Percent, not fixed money (user-raised).** Coupons discount a percent of the cart subtotal. `welcome10` = 10% off, not R$10 off. Money math: `discount = (subtotal × percent / 100)`, rounded **half-up** to cents, computed in one place (`Cart.discount()`). Orders record the resulting granted money, so the wire contract (`discount` as money `str`) is unchanged.
3. **Honor once applied.** Expiry is enforced at apply time only — inside `Coupon.add(cart, now)`. A coupon that expires while sitting on a cart is still honored at checkout. `Checkout` never touches the coupons repo (regression test asserts this).
4. **Deep application (user-raised).** The usecase does not check expiry/validity. `Coupon.add(cart, now)` is the single entry: it refuses when expired (`ValueError` → 400), exhausted (`quantity <= 0`), or with an out-of-range percent (`ValueError` → 400), and attaches the snapshot in the same call. Existence is the only usecase-level concern (`CouponNotFound` → 404, mirroring `ItemNotFound` at add).
5. **Proportional by construction.** Percent is bounded to `0 < percent <= 100` (DB CHECK + `Coupon.add` gate), so `discount <= subtotal` always and `total = subtotal - discount >= 0`. No clamp needed — a 100% coupon makes the order free (discount == subtotal). Total can reach `0.00` but never go negative.
6. **Snapshot semantics** (same invariant family as `cart_items.unit_price` at add time): cart snapshots the coupon's **percent** at apply; the money discount is derived from the live subtotal everywhere (cart read, cart mutation responses, checkout). Order copies code + granted money discount at checkout. Later coupon edits affect only future applies.
7. One coupon per cart; re-applying replaces; `DELETE` removes. Unknown code → `CouponNotFound` (404, mirrors `ItemNotFound` at add). Expired/exhausted/invalid → `ValueError` (400). Code normalized `strip().upper()` at the HTTP boundary (seed code `WELCOME10`, typed `welcome10` works).
8. Coupon is its own entity with the fields: `coupon_code`, `percent`, `expiry_time`, `created_at`, `updated_at`, plus `quantity` (remaining paid redemptions — usage limit). No min-purchase, no single-use flag, no fixed money value.
9. FK `carts.coupon_code → coupons(coupon_code)` (carts are transient; coupons are append-only — no delete feature, expiry is the lifecycle). Orders carry plain snapshot columns, **no FK** — order is history and must survive anything.
10. **Usage limit (user-raised).** Mirror the `items.stock` / `consume_stock` pattern: `coupons.quantity` decremented by one per paid redemption, atomically row-locked in the checkout transaction. Two gates:
    - Apply (`Coupon.add`) refuses an exhausted coupon (`quantity <= 0` → 400) — coupons are append-only, so 0 is terminal; an immediate, clear refusal beats a guaranteed checkout failure later.
    - Checkout consumes the use **after** the payment attempt succeeds, still inside the transaction. A failed consume (a concurrent checkout took the last use) rolls the whole order back — no paid order without its coupon use, never more redemptions than `quantity`. The race between apply and checkout is the checkout gate's job, exactly like oversold stock.
    The order row's `coupon_code` is the redemption audit trail; `quantity` is the counter.

## Design refinements forced by the invariants

**A. Snapshot semantics differ per table — say so in schema comments:**
- `coupons.percent` — the discount percent an operator sets (10 = 10% off).
- `carts.coupon_percent` — the percent **snapshotted at apply**; the granted money discount is derived live (`min`-free: percent <= 100 guarantees discount <= subtotal).
- `orders.coupon_discount` — the money discount **actually granted** at checkout (quantized cents), with `coupon_code` beside it.
Domain: `Cart.coupon_percent` (snapshot, plain int field), `Cart.discount()` (money, derived), `Order.coupon_discount` (granted money). Wire: `discount` = granted/effective money everywhere — the frontend never sees a percent.

**B. `Cart.total()` changes meaning from "sum of lines" to "payable".** `subtotal()` becomes the line sum; `total() = subtotal() - discount()`. With no coupon applied (`coupon_percent == 0`) behavior is byte-identical to today (`discount() == 0.00`). Existing `CartResponse.total` and checkout `Order.total` keep meaning "amount charged" — no frontend math changes. `subtotal()` sums with a `Decimal("0")` accumulator so an empty cart yields `Decimal`, never `int` (bare `sum()` returns `0` on an empty list, which broke the Decimal-only math below).

**C. Money rounding is half-up, in one place.** `Cart.discount()` = `(subtotal * percent / 100).quantize(Decimal("0.01"), ROUND_HALF_UP)`. Every consumer (cart reads, mutation responses, checkout) goes through it, so the number shown on the cart screen always equals what the order records. No per-line allocation: the discount is computed on the aggregate subtotal once.

**D. No revalidation at checkout is safe because the percent is snapshotted, not derived.** The alternative (join the live coupon at checkout) would need the coupons repo in `GetCart` + every cart mutation + `Checkout`, and would let a mid-session coupon edit silently change what the customer was shown. Snapshot keeps the coupons repo at exactly one call site (apply) — checkout only redeems.

**E. Redemption sits after the payment attempt, inside the same transaction.** With today's simulated gateway (payment is a DB row that succeeds or fails in-txn), consume-before-payment would also be safe — rollback covers a declined payment. The after-payment placement is deliberate: it encodes the real-world invariant that redemption is a **paid-event side effect**, so a future real gateway that approves outside the DB transaction cannot end up consuming coupons for orders that never got paid. Lock ordering in `Checkout` stays consistent: item rows (sorted by id) → coupon row — every checkout takes the same lock path, so no deadlock. A failed consume raises after the order + payment rows were written but the transaction rolls back, so nothing partial survives (same guarantee as the stock gate).

## Invariants (the TDD targets)

1. **Apply gate (deep).** Existence → `CouponNotFound` (404) is the only usecase check (repo's seam, `ItemNotFound` precedent). Expiry (`now >= expiry_time`), exhaustion (`quantity <= 0`), and out-of-range percent (`not 0 < percent <= 100`) → `ValueError` (400) are raised inside `Coupon.add(cart, now)`; the usecase performs none of these checks itself. On failure nothing persists and the cart is untouched.
2. **Percent money math:** `discount == (subtotal × percent / 100)` quantized half-up to cents; `0 <= discount <= subtotal`; `total == subtotal - discount`; `total >= 0`. Holds at every cart read and at checkout; 100% → discount == subtotal → total 0.00.
3. **Snapshot:** apply stores the coupon's `percent` verbatim on the cart (int); checkout grants the money discount derived from the cart's live subtotal; order persists `coupon_code` + granted; `order.total == sum(order_items totals) - order.coupon_discount`.
4. **Honor-once + paid redemption.** Checkout never *revalidates* the coupon (no `get_by_code` — assert not called); an applied-then-expired coupon still checks out with its discount. Redemption is the only coupon-touching call: `uow.coupons.consume(coupon_code)` awaited exactly once, after `payments.create`, inside the same transaction. A declined payment → consume never called. An exhausted consume → `ValueError`, and the whole checkout (order + payment + stock) rolls back.
5. **Replace/remove:** re-apply overwrites code+percent; remove clears both back to NULL/0.
6. **Never oversold coupon:** `quantity` never goes negative; exactly one decrement per paid order; the redeeming order's `coupon_code` is the audit trail back to the counter.

`domain/coupon.py`:
```python
from dataclasses import dataclass
from datetime import datetime

from .cart import Cart


@dataclass(frozen=True)
class Coupon:
    """Operator-issued discount code. Application rules live here, not in usecases."""

    coupon_code: str
    discount_percent: int  # percent off the cart subtotal (10 = 10% off)
    expiry_time: datetime
    quantity: int  # remaining paid redemptions; decremented per paid order
    created_at: datetime | None = None
    updated_at: datetime | None = None

    def add(self, cart: Cart, now: datetime) -> None:
        """Attach this coupon to a cart if still usable at `now`; else refuse.

        The single deep entry for applying: the applicability gates (not
        expired, uses left, sane percent) and the snapshot attach happen here,
        so the usecase never checks validity itself. `now` is injected to keep
        the rule pure and testable; the usecase passes `datetime.now()`. The
        cart snapshots discount_percent verbatim — a coupon edited later never
        changes what an applied cart charges. Quantity is only gated here; the
        authoritative decrement happens at paid checkout (consume).
        """
        if now >= self.expiry_time:
            raise ValueError(f"Coupon {self.coupon_code!r} expired at {self.expiry_time}")
        if self.quantity <= 0:
            raise ValueError(f"Coupon {self.coupon_code!r} has no remaining uses")
        if not 0 < self.discount_percent <= 100:
            raise ValueError(
                f"Coupon {self.coupon_code!r} discount must be between 1 and 100 percent"
            )
        cart.apply_coupon(self.coupon_code, self.discount_percent)
```

`domain/cart.py` — new fields + methods (no Coupon import; the attach step takes plain values so `coupon.py → cart.py` stays one-way):
```python
@dataclass
class Cart:
    session_id: str
    items: list[CartItem] = field(default_factory=list)
    handed_off_at: datetime | None = None
    coupon_code: str | None = None
    coupon_percent: int = 0  # snapshot of coupon percent at apply (10 = 10% off)
    id: int | None = None

    def apply_coupon(self, coupon_code: str, discount_percent: int) -> None:
        """Attach a coupon snapshot. Called by Coupon.add after its rules pass;
        re-apply replaces. No validation here — the gate owns it."""
        self.coupon_code = coupon_code
        self.coupon_percent = discount_percent

    def remove_coupon(self) -> None:
        self.coupon_code = None
        self.coupon_percent = 0

    def subtotal(self) -> Decimal:
        """Sum of line prices (the full-price story)."""
        return sum((ci.total() for ci in self.items), Decimal("0"))

    def discount(self) -> Decimal:
        """Effective discount: coupon percent of the subtotal, rounded half-up
        to cents. Percent is capped at 100 at apply, so the discount can never
        exceed the subtotal."""
        return (self.subtotal() * self.coupon_percent / 100).quantize(
            Decimal("0.01"), rounding=ROUND_HALF_UP
        )

    def total(self) -> Decimal:
        """Payable total after coupon discount."""
        return self.subtotal() - self.discount()
```

```python
from datetime import datetime

from src.domain.cart import Cart
from src.domain.exceptions import CartNotFound, CouponNotFound
from src.domain.repositories import UnitOfWork


class ApplyCoupon:
    """Attach a coupon to a cart, snapshotted at apply time.

    Thin by design: the only concern here is existence (404). Expiry, the
    uses-left gate, the percent range, and the snapshot attach are Coupon.add's
    job — the deep entry that owns the rules. Once applied the percent is
    locked; checkout honors it without re-reading the coupon (see Checkout).
    """

    def __init__(self, uow: UnitOfWork):
        self._uow = uow

    async def execute(self, session_id: str, coupon_code: str) -> Cart:
        async with self._uow as uow:
            cart = await uow.carts.get_by_session_id(session_id)
            if cart is None:
                raise CartNotFound(f"Cart for session {session_id!r} not found")

            coupon = await uow.coupons.get_by_code(coupon_code)
            if coupon is None:
                raise CouponNotFound(f"Coupon code {coupon_code!r} not found")

            coupon.add(cart, datetime.now())  # applicability gates + snapshot attach, one call
            await uow.carts.update(cart)
            return cart
```

`coupon_repository.py` (mirror cart_repository structure):
```python
import asyncpg

from src.domain.coupon import Coupon
from src.domain.repositories import CouponRepository


class PostgresCouponRepository(CouponRepository):
    """PostgreSQL implementation of the CouponRepository interface."""

    def __init__(self, conn: asyncpg.Connection):
        self._conn = conn

    async def get_by_code(self, coupon_code: str) -> Coupon | None:
        row = await self._conn.fetchrow(
            "SELECT coupon_code, percent, expiry_time, quantity, "
            "created_at, updated_at FROM coupons WHERE coupon_code = $1",
            coupon_code,
        )
        if not row:
            return None
        return Coupon(
            coupon_code=row["coupon_code"],
            discount_percent=row["percent"],
            expiry_time=row["expiry_time"],
            quantity=row["quantity"],
            created_at=row["created_at"],
            updated_at=row["updated_at"],
        )

    async def consume(self, coupon_code: str) -> None:
        # FOR UPDATE: within the checkout transaction this row-locks the coupon
        # so concurrent redemptions serialize — exactly one can take the last
        # use; the loser reads the decremented quantity and fails the check.
        # Only the paid checkout calls this, so a row can never be missing here
        # (the cart FK guarantees the coupon exists); defensive ValueError anyway.
        row = await self._conn.fetchrow(
            "SELECT quantity FROM coupons WHERE coupon_code = $1 FOR UPDATE",
            coupon_code,
        )
        if row is None:
            raise ValueError(f"Coupon {coupon_code!r} not found")
        if row["quantity"] <= 0:
            raise ValueError(f"Coupon {coupon_code!r} has no remaining uses")
        await self._conn.execute(
            "UPDATE coupons SET quantity = quantity - 1 WHERE coupon_code = $1",
            coupon_code,
        )
```

## Risks / tradeoffs / open notes

- **Honor-once is a merchant-policy choice** (user-approved): an applied coupon that expires while the cart lingers is still granted at checkout. If policy ever changes to revalidate at pay time, the seam is `Checkout` — add a coupon read there; the snapshot columns already keep the audit trail.
- **Percent snapshot, live money:** the cart stores the percent, so the money discount follows the subtotal until checkout (removals shrink it, additions grow it back). What the customer sees on the cart screen is always exactly what the order will record — same `Cart.discount()` on both paths.
- **Rounding convention:** half-up on `subtotal × percent / 100`, computed once on the aggregate (no per-line allocation). A 100%-off coupon is allowed and yields a `0.00` order; percent > 100 is rejected at apply and by the DB CHECK.
- **Lingering carts keep discounts indefinitely** until the (accepted-debt) cart TTL job lands; expiry only gates apply, not checkout. Same accepted debt class as lingering carts today.
- **Coupons are append-only** (no delete/admin feature). `expiry_time` is the lifecycle. The carts FK means a referenced coupon cannot be deleted even by SQL accident; orders carry no FK so history survives.
- **Local dev DB reset** (Tasks 1, and again for the percent change) wipes the docker volume — sanctioned by AGENTS (no deployed DB). Confirm no other workflow depends on that volume before `down -v`.
- **Schema truth drift:** coupons are woven into 001 (consolidated final shape per repo convention) rather than appended as new files — the file's "single source of truth" claim stays true. Requires the one-time reset per edit; future consolidations of later features follow the same path.
- `carts.coupon_percent` (snapshot) vs `orders.coupon_discount` (granted money) intentionally differ; schema comments carry the distinction, and `Cart.discount()` is the single money-derivation point.
- **Exhausted-at-checkout UX:** a coupon that ran out between apply and pay aborts checkout with a 400 ("no remaining uses") and the whole transaction rolls back; the customer removes the coupon and pays full price. Same failure shape as the existing oversold-stock gate — no silent charge changes, no free ride.
- **Redemption ordering note:** with the simulated in-txn payment, consume-before-payment would be outcome-identical (rollback covers declines). The after-payment placement is the real-world guard for a future out-of-txn gateway (refinement E). The infra `consume` row-lock (FOR UPDATE) is what guarantees only one checkout takes the last use under true concurrency; the single-thread live proof (Task 8.6) demonstrates the loser path, the lock is exercised by the same mechanism the stock gate already uses.
